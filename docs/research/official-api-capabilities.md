# Official Bangumi API capabilities

Research sidecar for PR-7A. This note describes the pinned v0 OpenAPI contract and compares it with the current curated semantic tools in BangumiAgentKit. It is not a proposal for PR-7B and contains no implementation changes.

## Sources and evidence conventions

Verified against:

- Repository-pinned specification: [`openapi/upstream/v0.yaml`](../../openapi/upstream/v0.yaml).
- Upstream API mirror of that specification: [`bangumi/api/open-api/v0.yaml`](https://github.com/bangumi/api/blob/master/open-api/v0.yaml). The API repository says that this file is synchronized from `bangumi/server`; this is the primary contract used here.
- Upstream server handlers: [`bangumi/server/web/handler`](https://github.com/bangumi/server/tree/master/web/handler), especially [subject handlers](https://github.com/bangumi/server/tree/master/web/handler/subject), [character handlers](https://github.com/bangumi/server/tree/master/web/handler/character), [person handlers](https://github.com/bangumi/server/tree/master/web/handler/person), [user handlers](https://github.com/bangumi/server/tree/master/web/handler/user), [index handlers](https://github.com/bangumi/server/tree/master/web/handler/index), and [revision handlers](https://github.com/bangumi/server/blob/master/web/handler/revision.go).
- Current semantic surface: [`packages/tools/src/definitions/read-tools.ts`](../../packages/tools/src/definitions/read-tools.ts), [`write-tools.ts`](../../packages/tools/src/definitions/write-tools.ts), [`raw-operation-tools.ts`](../../packages/tools/src/definitions/raw-operation-tools.ts), [`registry.ts`](../../packages/tools/src/registry.ts), and the service implementations under [`packages/bangumi-core/src/services`](../../packages/bangumi-core/src/services).

“Verified” means directly represented in the pinned OpenAPI or observed in the cited repository source. “Inference” means an interpretation added for this comparison, principally write-risk labels or a semantic-tool coverage judgment. Security below reports the OpenAPI declaration: an absent `security` field means no security scheme is declared for that operation; `OptionalHTTPBearer` means a bearer token may be supplied; `HTTPBearer` means it is required, with the listed scopes.

The pinned document contains 55 operations. All v0 operations are read-only except the explicit collection, index, and character/person collect mutations identified below. `POST` search operations are classified as reads because their server handlers delegate to search and return results without changing state.

## Shared response shapes

These names are the schemas used in the operation inventory. Unless a response says otherwise, the OpenAPI also declares `ErrorDetail` for the listed 400/401/404 cases; it contains `title`, `description`, and `details` (string or object).

- `Paged<T>`: `total`, `limit`, `offset`, and `data: T[]`. The pinned schemas instantiate it as `Paged_Subject`, `Paged_Character`, `Paged_Person`, `Paged_Episode`, `Paged_Revision`, `Paged_UserCollection`, `Paged_UserCharacterCollection`, and `Paged_UserPersonCollection`.
- `Subject`: `id`, `type`, `name`, `name_cn`, `summary`, `series`, `nsfw`, `locked`, optional `date`, `platform`, `images`, `infobox`, `volumes`, `eps`, `total_episodes`, `rating`, `collection`, `meta_tags`, and `tags`. `rating` and `collection` are intentionally open objects in the spec; the current server response maps rating/collection statistics into these objects. `tags` contains `name`, `count`, and `total_count`.
- `SlimSubject`: compact subject data: `id`, `type`, `name`, `name_cn`, `short_summary`, optional `date`, `images`, `volumes`, `eps`, `collection_total`, `score`, `rank`, and `tags`. It is nested in `UserSubjectCollection`.
- `Episode`: `id`, `type`, `name`, `name_cn`, `sort`, optional `ep`, `airdate`, `comment`, `duration`, `desc`, `disc`, and optional `duration_seconds`. `EpisodeDetail` has the same core fields plus required `subject_id` and no `duration_seconds` in the pinned schema.
- `Character`: `id`, `name`, `type`, optional `images`, `summary`, `locked`, optional `infobox`, `gender`, `blood_type`, `birth_year`, `birth_mon`, `birth_day`, and `stat` (`comments`, `collects`). `Person` is the compact person form (`id`, `name`, `type`, `career`, optional `images`, `short_summary`, `locked`); `PersonDetail` adds `summary`, `last_modified`, infobox and parsed birth/gender/blood fields, and `stat`.
- Relationship records are explicit: `RelatedPerson` has person identity/images, `type`, `career`, `relation`, and `eps`; `RelatedCharacter` has character identity/images, `summary`, `relation`, and `actors`; `v0_subject_relation` has subject identity, images, and `relation`; `v0_RelatedSubject` has subject identity, `staff`, `eps`, and `image`; `CharacterPerson` and `PersonCharacter` carry the related subject identity (`subject_id`, `subject_type`, `subject_name`, `subject_name_cn`) plus staff/role information.
- `User`: `id`, `username`, `nickname`, `user_group`, `avatar` (`large`, `medium`, `small`), and `sign`. The schema notes that an undocumented `url` may occur but is not a client contract.
- `UserSubjectCollection`: `subject_id`, `subject_type`, `rate`, `type`, `tags`, `ep_status`, `vol_status`, `updated_at`, `private`, optional `comment`, and nested `subject: SlimSubject`.
- `UserEpisodeCollection`: nested `episode: Episode`, `type` (`0` uncollected, `1` wish, `2` done, `3` dropped), and `updated_at` as a Unix timestamp. The subject-level episode collection is `Paged<UserEpisodeCollection>`.
- Character/person collection records contain `id`, `name`, `type`, images, and `created_at`; person records also contain `career`.
- `Revision`: `id`, `type`, `creator`, `summary`, and `created_at`. Detail revisions add `data`; `DetailedRevision.data` is explicitly open-ended. The person/character/subject detail schemas specialize the shape of `data`.
- `Index`: `id`, `title`, `desc`, optional `total`, `stat` (comments/collects), `created_at`, `updated_at`, `creator`, `ban`, and `nsfw`. `IndexSubject` contains `id`, `type`, `name`, optional images/infobox/date, `comment`, and `added_at`.

## Complete v0 operation inventory

Risk is an **inference for this research note**: `read` does not mutate server state, `write` changes a collection/index or creates a relationship, and `destructive` removes an existing relationship or index membership. The OpenAPI itself supplies the method, path, input schema, response schema, and security declaration, not this risk vocabulary.

### Raw fallback and non-semantic tools

- `bangumi.list_operations`, `bangumi.describe_operation`, and `bangumi.call_operation` are not semantic domain tools. They expose the generated `OPERATION_REGISTRY`; the registry contains all 55 pinned operations, including method/path, path/query metadata, auth, scopes, and generated risk. `call_operation` accepts arbitrary `pathParams`, `queryParams`, and `body` values and dynamically invokes the generated client operation.
- The raw tool is gated: read operations are callable through it, while non-read operations are rejected unless `BANGUMI_ALLOW_RAW_WRITES=true`; the curated write tools remain the intended write path. This is verified in `packages/tools/src/definitions/raw-operation-tools.ts`.
- Auth tools (`bangumi.auth_*`) manage the agent’s OAuth/account binding and are not Bangumi v0 API operations. Render tools are presentation wrappers; they call selected read operations and/or legacy calendar, then save an artifact.

## Coverage and gaps

### Direct semantic coverage

The curated tools directly cover these v0 operation families:

- Search: all three search operations, but with narrower filters than the official bodies.
- Subject: subject detail and subject-to-subject relations; subject persons/characters are covered indirectly through `get_subject_cast`, which currently uses the character relation endpoint and its nested actors rather than the separate subject-person operation.
- Episodes: list/detail reads, plus the subject episode collection mutation used by progress updates.
- Character/person: detail, search, selected relationships, and collect/uncollect writes.
- User/subject collections: current profile, public/current collection list, single collection, subject collection write, and episode-progress write.
- Revisions: all list/detail operations through unified entity-type tools.
- Indices: index detail/list reads and create/edit/add/remove writes.

### Official operations not exposed by a dedicated semantic tool

These remain available only through the raw fallback (or through lower-level services where noted):

- `getSubjects` (`GET /v0/subjects`) browsing with category/year/month/platform/series filters.
- `getSubjectImageById`, `getCharacterImageById`, `getPersonImageById`, and `getUserAvatarByName` redirect/image operations.
- `getRelatedPersonsBySubjectId` as a separate operation; the semantic cast path returns character relations with nested actors instead.
- `getUserSubjectEpisodeCollection` and `getUserEpisodeCollection` authenticated episode-status reads.
- `patchUserCollection` as a distinct PATCH operation; the semantic update tool uses POST.
- `putUserEpisodeCollection` for a single episode status update.
- Public character/person collection list/detail operations.
- `editIndexSubjectsByIndexIdAndSubjectID` (including `sort`/`comment`).
- `collectIndexByIndexIdAndUserId` and `uncollectIndexByIndexIdAndUserId`.

This list is a coverage observation, not a recommendation to add tools. It also does not count the legacy `/calendar` endpoint as v0 coverage.

### Important contract mismatches or narrowing

- The official search bodies support substantially more filters than curated tools expose: subject tags/ranges/date/rank, character NSFW, and person career.
- The official subject browser is not represented by the semantic surface; `search_subjects` is not a substitute because it is a different POST search contract.
- Several official image operations return redirects and are absent from the semantic surface; they are not ordinary JSON detail reads.
- Official collection writes permit `private`, book volume/episode progress fields, tag-clearing semantics, and separate POST/PATCH behavior. `update_collection` intentionally presents a narrower semantic input.
- Official episode collection reads are distinct from episode metadata reads. Current semantic tools can write progress but do not offer the authenticated collection read operations.
- The pinned spec does not describe a response schema for `getIndexSubjectsByIndexId`; the upstream server source does return paged index-subject data. This is a verified source/spec discrepancy, not an inferred schema change.
- The generated operation registry uses coarse request-body metadata (`required` only) and its own derived risk/auth metadata. The authoritative field-level body contract in this note is the pinned OpenAPI schema; the authoritative curated-tool behavior is the current TypeScript source.

## Bottom line

The official v0 API is broader than the curated semantic surface: 55 operations cover public metadata/relationships, authenticated collection reads and writes, revision history, and index management. BangumiAgentKit’s semantic layer deliberately compresses that into user-oriented search/detail/progress/collection/index tools, while preserving full operation reachability through the raw fallback. The main unrepresented official capability clusters are browse/image endpoints, detailed episode-collection reads and single-episode writes, person/character collection reads, index membership editing/collection, and the richer search filters.
