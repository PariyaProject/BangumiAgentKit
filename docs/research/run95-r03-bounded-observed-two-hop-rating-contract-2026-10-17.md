# Run #95 R03 — bounded observed two-hop rating contract

**Disposition: `IMPLEMENTATION_READY` for a bounded observed-sample result only.** The available fields support ranking candidates with a positively observed directed path and a successfully read rating. They do **not** support a full-graph winner, completeness claim, canonical relation order, or a claim that unreturned paths do not exist.

**Scope:** source-only review dated 2026-10-17 against the current public Bangumi v0 reference/OpenAPI and this repository snapshot at `d59fab61d970f810d4ed67cd873749d6a9a04b46`. No live API requests were made.

## Supported contract

- Current official `GET /v0/subjects/{subject_id}/subjects` takes the subject path parameter and documents a `200` JSON **array** of `v0_subject_relation`; it has no `limit`, `offset`, page envelope, or `total` field. Relation rows provide `id`, `type`, `name`, `name_cn`, `relation`, and optional `images`. The documented contract gives no graph-completeness or ordering semantics. [Official v0 API reference](https://bangumi.github.io/api/) · [current API OpenAPI](https://github.com/bangumi/api/blob/master/open-api/v0.yaml#L452-L482) · [relation-row schema](https://github.com/bangumi/api/blob/master/open-api/v0.yaml#L4114-L4157) · [pinned repository spec](../../openapi/upstream/v0.yaml#L462-L490) · [pinned relation-row schema](../../openapi/upstream/v0.yaml#L4131-L4157).
- Subject detail `GET /v0/subjects/{subject_id}` returns `Subject`; its `rating` object includes numeric `score`, integer `total`, `rank`, and the 1–10 count buckets. The operation documents a 300-second cache. The repository’s `bangumi.get_subject_stats` provider reads this same subject-detail operation and maps those fields; it is not a separate rating source. [official detail operation](https://github.com/bangumi/api/blob/master/open-api/v0.yaml#L321-L350) · [official rating schema](https://github.com/bangumi/api/blob/master/open-api/v0.yaml#L3628-L3671) · [pinned rating schema](../../openapi/upstream/v0.yaml#L3645-L3686) · [local stats provider](../../packages/provider-core/src/providers.ts#L1319-L1343).
- The repository relation tool preserves the source-to-returned-target direction and raw relation labels, and already says the interface has no pagination, total, reverse/transitive coverage, or canonical order. Its underlying `SubjectService` can apply a local row limit and optional `maxResponseBytes`; the row limit is applied **after** the full array has been received. The current tool call supplies neither limit nor byte cap, and the transport defaults an omitted byte cap to infinity. [relation tool contract](../../packages/tools/src/definitions/read-tools.ts#L471-L515) · [service limits](../../packages/bangumi-core/src/services/subject-service.ts#L350-L389) · [transport default](../../packages/bangumi-transport/src/http-client.ts#L254-L258).

## Limits and policy

The missing upstream pagination means a local row cap alone does not bound the downloaded response. A safe implementation must set a hard body-byte cap on **each** relation and detail response before parsing, plus local traversal and candidate caps. A body that exceeds the cap is a failed/unavailable observation, not an empty relation list or zero score. The repository transport supports hard byte caps when callers pass them, and another bounded source path uses 1 MiB; relation and stats calls currently do not pass that limit. [transport cap implementation](../../packages/bangumi-transport/src/http-client.ts#L30-L33) · [existing 1 MiB convention](../../packages/bangumi-core/src/services/person-activity-service.ts#L281).

Bangumi’s published User-Agent guidance asks non-browser clients to identify the developer and application, add a version for distributed apps, and include a project URL for open-source apps; it warns generic library defaults may be disabled. The checked official API docs/OpenAPI publish no numeric per-request quota for these operations, so that absence is not an unlimited-rate allowance. Use a small local request budget, one request at a time, and stop/back off on rate-limit errors. The current repository transport retries retryable read-only failures up to twice (including HTTP 429), so an implementation’s budget must count retries as wire attempts. [official User-Agent guide](https://github.com/bangumi/api/blob/master/docs-raw/user%20agent.md) · [local retry behavior](../../packages/bangumi-transport/src/retry.ts#L9-L58) · [429 handling](../../packages/bangumi-transport/src/http-client.ts#L170-L191).

## Bounded salvage variant

Implement a result described as **“highest observed rating among the bounded, successfully rated candidates reached from the supplied subject by up to two returned outgoing relation rows.”** One concrete budget is: cap every response at 1 MiB; inspect at most 24 valid root rows; fetch relations for at most 4 selected first-hop subjects; inspect at most 8 returned rows per selected intermediate; and fetch detail for at most 16 unique candidate IDs across depths one and two. Exclude the input subject itself and deduplicate remaining candidates by ID. That is at most 21 logical GET operations (one root relation read, four intermediate relation reads, and sixteen detail reads), performed serially; with the current two-retry transport default, bound the worst case at 63 outbound attempts. These are local sampling limits, not Bangumi server limits.

Include only candidates with at least one observed directed path from the root and a successful detail response with finite `rating.score > 0` and `rating.total > 0`. Deduplicate by subject ID; retain the path’s raw relation labels and depth. Rank by the returned numeric score, show rating total and retrieval time, and preserve equal scores as ties. Explicitly report observed/selected/omitted relation rows, selected intermediates, detail reads/failures, truncation, and the bounded request budget. A top entry means only **highest in the successfully rated bounded sample**; omitted paths, oversize responses, missing ratings, and failed detail reads remain unknown. The detail endpoint’s documented cache also means the score is an observation returned during this request, not a synchronized real-time snapshot.

## Disposition boundary

A safe implementation-ready variant exists because each returned relation row identifies a target and each target’s subject detail supplies a numeric observed score. No full-graph maximum, graph completeness, absence, or official/canonical path or tie order is supported by these sources. If the product needs that stronger claim, this source contract is insufficient.
