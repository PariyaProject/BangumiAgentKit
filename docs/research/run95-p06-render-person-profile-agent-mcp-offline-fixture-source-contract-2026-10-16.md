## Finding

A fresh isolated synthetic fixture can exercise the local `bangumi.render_person_profile` Agent/MCP tool path with **zero live Bangumi API, OAuth, or renderer-asset requests**, if it injects a strict local `fetchFn` into the public `HttpClient`, supplies an image-free synthetic person, leaves chronology disabled, and rejects every request outside the exact expected routes or any `Authorization` header. The tool itself makes three v0 reads; those are local stub invocations, not live requests. This claim is limited to the Bangumi/application data plane. It does not establish zero network activity for the whole Agent run: the C07 pattern invokes Codex and Harness/GitHub control-plane operations, and its source does not install an operating-system-wide network sandbox. ## Input contract and execution path

`bangumi.render_person_profile` is a read-only tool with `auth: none` and no scopes. Its required `personId` is a positive integer. Optional bounds are `maxSubjects` 1–500, `maxCharacters` 1–500, `maxCredits` 1–20, `includeChronology` boolean, and `maxChronologySubjects` 1–48. Defaults in execution are 500 subjects, 500 characters, chronology off, 48 chronology details if enabled, and 8 displayed credits per relation type. [Tool definition](../../packages/tools/src/definitions/render-presentation-tools.ts#L742-L783)

The MCP call is validated by `ToolRegistry` before execution. The registry only resolves an authenticated client for `auth: required` or `auth: optional`; this renderer is `auth: none`. It then obtains the public client and creates `PersonService`. `getPersonProfile` concurrently calls `GET /v0/persons/{person_id}`, `GET /v0/persons/{person_id}/subjects`, and `GET /v0/persons/{person_id}/characters`. These generated operations have no query parameters. [Registry auth handling](../../packages/tools/src/registry.ts#L285-L315), [generated endpoint paths](../../packages/bangumi-openapi/src/generated/index.ts#L276-L321), [operation metadata](../../packages/bangumi-openapi/src/operation-registry.ts#L324-L372), [profile service](../../packages/bangumi-core/src/services/person-service.ts#L510-L547)

The two `max*` relation limits are applied after each complete response has arrived: the service maps all rows, then slices locally. They do not cap response size or upstream row count. With `includeChronology: true`, the service can make additional `GET /v0/subjects/{id}` calls for sampled anime rows, up to 48, with concurrency capped at four. A fixed offline acceptance should set `includeChronology: false`; a fixture intended to count exactly three data calls must return small synthetic arrays and must not mistake local slicing for API pagination. [Relation slicing and chronology branch](../../packages/bangumi-core/src/services/person-service.ts#L514-L538), [chronology detail calls and limits](../../packages/bangumi-core/src/services/person-service.ts#L549-L575)

## Offline boundary and required fixture shape

The C07 one-tool server constructs an `HttpClient` with base URL `https://api.bgm.tv` and injects its fixture as `fetchFn`. Runtime dependencies reuse that exact client as `publicHttpClient`; `TokenBroker.getPublicClient()` only constructs a generated client around it. A P06 fixture can therefore return local synthetic JSON for the three exact person routes without opening an API connection. [C07 MCP server client wiring](../../apps/mcp/codex-one-tool-mcp-server.mjs#L260-L276), [runtime dependency wiring](../../packages/tools/src/registry.ts#L99-L131), [public client construction](../../packages/auth/src/token-broker.ts#L198-L200)

The current C07 fixture is fail-closed in the relevant ways: it checks for `Authorization`, counts and rejects it, accepts only exact known operations, counts unexpected requests, and returns an error response for any unknown operation. Its tests assert the expected local request count, zero authorization headers, zero unexpected requests, and complete expected operations. A new P06 fixture should mirror those properties with its own profile id and only the three exact `GET` paths for one fixed synthetic person ID; every other method/path, repeated call, query variation, or authorization header should be denied and counted. [C07 fixture allowlist and denial behavior](../../scripts/lib/c07-cohort-render-offline-fixture.mjs#L132-L203), [C07 local-call assertions](../../tests/integration/mcp-render-target.test.ts#L310-L334)

Image retrieval is a separate path from `HttpClient.fetchFn`. The person-profile view-model selects the first nonempty `large`, `medium`, or `small` person image. `RenderService` extracts that URL and sends it through `AssetResolver`, whose default transport makes native HTTP(S) requests. Thus the fixture must return empty image fields (or omit them), and its runner should assert the resulting image URL list is empty; otherwise the API stub alone does not establish offline rendering. The browser stage itself blocks service workers and aborts all Playwright page requests. [Person image projection](../../packages/renderer/src/view-model-builders/index.ts#L2544-L2556), [asset extraction and resolution](../../packages/renderer/src/render-service.ts#L78-L131), [native asset transport](../../packages/renderer/src/asset-resolver.ts#L251-L299), [Playwright request blocking](../../packages/renderer/src/browser-pool.ts#L142-L154)

For the C07-style runner, the one-tool MCP server strips credential-like environment variables, uses in-memory storage and artifact storage, and exposes only the configured tool after checking that the catalog labels it `auth: none` and `risk: read`. Those controls support anonymous, nonpersistent execution; the P06-specific fixture still needs its own exact tool/argument/profile guard. [Environment, storage, catalog, and tool setup](../../apps/mcp/codex-one-tool-mcp-server.mjs#L233-L280)

## Result and artifact projection

The service result is converted into a `person-profile` view-model containing the synthetic person's identity and summary, bounded subject/character credits, aggregate breakdowns, coverage counters, limitations, warnings, and retrieval time. It is passed to `renderAndSaveArtifact`, which stores PNG bytes and returns only `{ artifact: artifactRef }`; the returned reference contains metadata such as ID, MIME type, dimensions, and expiry, not the view-model or source rows. The MCP presenter has a special structured profile branch for `bangumi.get_person_profile`, not this renderer; the renderer's small artifact-reference result follows the normal JSON-text presentation path. [View-model projection](../../packages/renderer/src/view-model-builders/index.ts#L2473-L2618), [artifact return](../../packages/tools/src/definitions/render-presentation-tools.ts#L149-L184), [MCP result presentation](../../apps/mcp/src/result-presenter.ts#L107-L140)

The C07 runner's existing sanitized summary records artifact metadata and a digest rather than the image bytes or fixture payload. A P06 report should retain equivalent bounded artifact facts, fixture counters, exact call identity, and privacy assertions, but no raw synthetic response rows or PNG bytes. [C07 in-memory artifact summary](../../apps/mcp/codex-one-tool-mcp-server.mjs#L48-L118), [C07 result summary](../../scripts/lib/codex-one-tool-evidence.mjs#L642-L658), [C07 offline and artifact checks](../../scripts/acceptance/run-c07-cohort-renderer-codex-agent-mcp.mjs#L522-L584)

## C07 reuse boundary and acceptance claim

The fixture/server pattern is useful as an implementation reference, but the current network-mode guard accepts only the exact C07 renderer tool and its fixed arguments. It cannot be repurposed as a P06 profile. More importantly, the canonical frontier ledger records C07's final allowed fixture invocation as `INCONCLUSIVE`, says not to invoke its runner again, and keeps C07 `UNASSESSED`. Any future P06 run must have an independently selected identity/profile and its own one-shot disposition; this report does not start or authorize that run. [C07 exact-profile guard](../../scripts/lib/c07-cohort-render-offline-fixture.mjs#L1-L36), [terminal C07 frontier disposition](../../docs/product/frontier-ledger.json#L1982-L2003)

This synthetic renderer exercise could validate one bounded local Agent/MCP invocation, API-call stubbing, image-free rendering, artifact creation, and the returned artifact reference. It cannot establish whether a person's latest 20 works are ongoing, whether person relations are complete or ordered by recency, or any live Bangumi fact. The P06 frontier remains `UNASSESSED`; its stated scenario asks about the latest 20 and ongoing status, which `render_person_profile` does not compute. This static report adds no matrix, scenario, or Agent/MCP acceptance credit.
