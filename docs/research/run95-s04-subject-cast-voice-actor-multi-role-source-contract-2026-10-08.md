# Run #95 S04 — same cast person across multiple characters

Source snapshot: 2026-10-08, checkout `d744835fb5207081e255132e20107296a754fd36`. This is source-contract research only; no live API call or tests were run.

## Source contract and local behavior

- Official `GET /v0/subjects/{subject_id}/characters` takes only a subject ID and returns a bare JSON array of `RelatedCharacter`; the operation defines neither pagination parameters nor a total. The row schema declares `id`, `name`, `summary`, `type`, `images`, `relation`, and `actors`; all except `images` and `actors` are required, and `actors` defaults to an empty array. Each nested `Person` declares `id`, `name`, `type`, `career`, `images`, `short_summary`, and `locked` (all except `images` required). The local mapper keeps character ID/name/type/summary/images/relation and actor ID/name/career plus one selected actor image; it drops nested actor type, short summary, locked, and the other image variants. [Official operation](https://github.com/bangumi/server/blob/master/openapi/v0.yaml#L431-L461) · [Person schema](https://github.com/bangumi/server/blob/master/openapi/v0.yaml#L3181-L3218) · [RelatedCharacter schema](https://github.com/bangumi/server/blob/master/openapi/v0.yaml#L3391-L3429). Local mirror/mapping: `openapi/upstream/v0.yaml:L431-L461`, `L3181-L3218`, `L3391-L3429`, `packages/bangumi-core/src/services/character-service.ts:L238-L260`.
- `relation` is a required plain string on the character row. The schema gives it no enum or definition, so labels such as `主角` can be preserved as raw evidence but do not establish an official “main/lead role” taxonomy. `Person.career` is a person-level enum list that includes `seiyu` and `actor`; it classifies a person, not a particular character credit. [Official schemas](https://github.com/bangumi/server/blob/master/openapi/v0.yaml#L3203-L3230) [and](https://github.com/bangumi/server/blob/master/openapi/v0.yaml#L3391-L3429). Local mirror: `openapi/upstream/v0.yaml:L3203-L3230`, `L3421-L3429`.
- Both entity IDs are integers, and the current mapper preserves `character.id` and nested `actor.id`. The operational join is therefore by numeric actor/person ID across rows, with character IDs identifying roles; names are display text, not keys. Neither the source schema nor the mapper promises unique rows or unique actor links. The mapper preserves input duplicates, so count a set of distinct character IDs per actor ID and collapse duplicate `(actor ID, character ID)` links before counting. Local mapping/validation: `packages/bangumi-core/src/services/character-service.ts:L69-L97`, `L222-L270`; result mapping: `L238-L260`.
- Existing coverage verifies one GET and basic actor/relation mapping, but not repeated actor IDs across character rows. The cast answer checker keys by relation plus character name and compares actor names, so it cannot verify an ID-based multi-role grouping. `tests/semantic/semantic-tools.test.ts:L555-L593`; `scripts/acceptance/subject-cast-answer-check.mjs:L108-L166`.
- `bangumi.get_subject_cast` requires one known `subjectId`; `limit` defaults to 30 and accepts at most 100. The service reads the full array once, filters schema-valid rows, then selects the first `limit`; `observed` is the response-array length, `returned` is the selected valid-row count, and `truncated` covers either local row drops or schema drift. Invalid nested actor IDs are counted separately and can overlap schema-drift rows. The tool does not pass a response-byte cap; transport defaults to no byte limit when `maxResponseBytes` is omitted. Local limits and coverage: `packages/tools/src/definitions/read-tools.ts:L572-L589`, `packages/bangumi-core/src/workflows/subject-cast.ts:L27-L56`, `packages/bangumi-core/src/services/character-service.ts:L222-L270`, `packages/bangumi-transport/src/http-client.ts:L236-L240`.
- The MCP text view is capped at 3,600 UTF-8 bytes. When compacted, it starts with at most four cast rows and two actors per character, then reduces that projection if needed; it reports omitted rows/actors and preserves the full result in `structuredContent`. Compact text also omits actor career. Thus a text-only answer may establish a positive from included IDs, but cannot enumerate every multi-role actor when rows or actor links were omitted, or verify `seiyu` career evidence from a compact result. `apps/mcp/src/result-presenter.ts:L16`, `L81-L92`, `L2711-L2782`; cast dispatch and structured output: `L137-L142` and `apps/mcp/src/server.ts:L254-L265`.
- A successful malformed/non-array body degrades into zero returned rows with schema drift and truncation. Although OpenAPI does not require `actors`, local row validation does; an omitted actor array or a malformed nested actor therefore excludes the character row rather than treating it as actorless. HTTP, network, parse, and configured size errors propagate rather than becoming an empty cast; the MCP wrapper returns `isError: true`. `packages/bangumi-core/src/services/character-service.ts:L69-L97`, `L232-L270`; `packages/bangumi-transport/src/http-client.ts:L145-L187`, `L199-L217`; `apps/mcp/src/server.ts:L267-L304`.

## Safe salvage and readiness

The original “which works” wording suggests discovery across works, and “main roles” adds a role classification. This endpoint only reads a supplied subject, and the official schema has no main-role taxonomy. The candidate safe statement is a useful, narrower answer for a user-named work: **within this subject’s currently observed, valid cast rows, the same actor person ID is linked to two or more distinct character IDs**, with each character’s raw `relation` label and all row/text omission caveats. If calling that person a voice actor, retain `career` as evidence and use the `seiyu` label only when the returned career list contains it; that still says nothing about whether the roles are main roles. This preserves the multi-casting question for a known title but loses S04’s broader work-discovery value, so it is a bounded subscenario rather than completion of catalog-wide discovery.

**Assessment: implementation-ready for the one-subject positive observation.** The existing service supplies the exact IDs and raw labels needed to derive it. It cannot discover matching works across Bangumi or support a negative/complete-list claim: one response has no page/total contract, local selection can drop rows, and the MCP text view can omit additional rows and actors. Even `truncated: false` means only that this response had no local/schema truncation; it does not certify a complete catalog cast. If no group is found, report only that none was established in the bounded observed set.
