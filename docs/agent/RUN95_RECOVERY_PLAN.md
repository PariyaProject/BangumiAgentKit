## Daily execution and handoff

1. Read AGENTS.md, PRODUCT_CHARTER.md, HARNESS.md and this plan.
2. Observe the Codex Goal through its tool. Run continuation:show with the
   observed goal-state. Read the exact active PR and profile disposition when
   the next step needs it.
3. Follow the latest structured directive. Record a genuinely new human
   continue/pause/replan instruction once with source reference and observed
   sequence. Never reinterpret an old pause quotation as a new order.
4. Choose one named package, explicit input/evidence basis and expected
   observable improvement. Read previous relevant checkpoints and findings.
5. Implement a coherent change, verify affected scope, inspect actual product
   output, then record one meaningful checkpoint. No heartbeat events or
   runtime-state Git commits.
6. At handoff, record outcome, evidence refs, unresolved cause and one next
   action. The next model starts with the compact brief, not the transcript.
7. Poll CI/review with bounded waits; unchanged polling is not progress.

Command schemas are in HARNESS.md §2a. App Goal paused/blocked, Run state,
Epoch state and reviewer runtime are independent observations. A repository
command cannot resume the app Goal. A manual planning request may complete
while automatic Goal continuation is paused.

## When to obtain strategy review

- Two consecutive no-progress attempts with the same problem and input basis,
  or three corrective verdicts since the last strategy review, require a
  strategy checkpoint before another review, extension or claim.
- Preserve a logical input fingerprint: contract/fixture/environment relevant
  to the failure. Changing only a Candidate SHA, profile name, date or output
  directory is not a new hypothesis.
- Record observed cause, rejected approaches, changed plan, evidence, actual
  reviewer identity/model and next action. "Continue", another test rerun or
  increased budget alone is not a resolution.
- Luna Max remains the daily worker and normal independent Product reviewer.
  A user-selected advanced model may perform the strategy review. It is
  supplementary; it cannot manufacture Product PASS or replace same-reviewer
  identity, budget or exact-SHA requirements.
- If the required model is unavailable, finish safe preparation and identify
  the missing capability honestly. Do not silently use Luna to self-certify an
  advanced review or mark the Goal completed/blocked just because one route waits.

## Design contract

Maintain a small set of stable systems, each with a distinct composition:

- Warm Editorial: warm paper, restrained hierarchy, rounded readable body type,
  illustration/cover integrated into reading order.
- Clean Gallery: light neutral surfaces, generous alignment, strong title or
  score focal point, open rows and restrained framing.
- Graphic Zine: cobalt/paper/coral palette, purposeful torn-paper grouping and
  overlap, controlled irregularity, coherent display type and semantic icons.

Light is the requested default direction. Dark remains selectable. Design
pack, palette, body/display font and scale are separate preferences; preserve
actual configuration through QQ → runner → renderer. Prove the loaded face,
not merely CSS font names.

For each template family, keep one reference board and one last reviewed
native baseline. Store hashes, content fixture, dimensions, font/weight/size,
icon family, palette tokens, asset placement and scope of user approval.
"Direction suitable" for font size is not approval of every template.
AI-generated references are not user acceptance.

Score each candidate 1–5 for hierarchy, typography, spacing/line breaks,
color/material, image/icon integration, and reference fidelity. Require at
least 4 in every category for the designer's release recommendation, plus:

- no clipped content, overlapping labels, isolated punctuation or accidental
  single-glyph lines; original names and meaningful values survive PNG output;
- titles, scores and metadata have a clear reading order;
- masks explain grouping and respect content, rather than decorating every box;
- partial/missing/conflict/long states remain legible and honest;
- icons share a family with text labels; no unrelated generated icon styles;
- public data, private state, formulas and limits remain distinct without an
  oversized technical-report block;
- verify the shared 0.75 scale at the intended 360 CSS px chat presentation.

Compare whole compositions side by side at identical content and scale. Fix
related findings in one batch. After two design batches without improvement,
change the composition hypothesis through strategy review; do not keep nudging
padding and font sizes indefinitely. Record user acceptance only when observed.

Use Hallmark for structure and critique, existing React/SVG/theme tokens and
the asset pipeline for implementation. Icon/component packages are welcome
when they improve consistency. Vite/Vue/Three.js/anime.js are options, not a
checklist: a static PNG gains nothing from an unobserved animation. GIF is a
later additive experiment with static fallback, reduced motion, byte/latency
bounds and real client compatibility evidence.

## Evidence, cost and engineering discipline

- Choose the cheapest relevant validation first. Reuse passing results only
  with unchanged relevant inputs. Do not rerun the full suite after editing a
  sentence, waiting for CI or switching models.
- A local layout change reviews every changed image and verifies untouched
  hashes. A shared font/theme/component change expands coverage to affected
  template families and stress states.
- Preserve exact Candidate/Base/CI delivery binding. Do not commit live
  "CI pending/passed" narration merely to refresh status and create another
  Candidate. Dated historical reports stay dated; live CI lives in GitHub.
- Before a one-shot, prove preconditions with ordinary synthetic diagnostics.
  Reconcile or preserve ambiguous/terminal latches; never retry them. Do not
  keep creating profiles to investigate the same failure.
- Keep bounded reason codes, stages/counters and hashes; no credentials,
  private payloads, raw conversations or throwaway terminal logs. Minimal
  sanitized replay fixtures should explain failures after cleanup.
- Delete only generated, regenerable files no longer needed by current/prior
  baselines or active review. Keep current evidence, relevant baseline and
  references. Inventory sizes and expected reclaimed bytes before cleanup.
- Continuation events append inside the existing Run Issue. Body limits fail
  visibly; never silently trim history or fall back to tracked runtime files.
  One writer, pre-write reread and post-write readback are required; GitHub
  body PATCH is not an atomic transaction.
